PART 1: ROOT CAUSE ANALYSIS - WHY ITERATION 7 BIOME RULES NEVER FIRED
================================================================================

1.1 THE DEFECT IN MapGenerator.Generate

Reading MapGenerator.cs lines 60-69 of the Iteration 7 codebase
reveals the discretization block:

   torch.Tensor generatedCpu = generated.cpu();
   List<TileMap> maps = new List<TileMap>();
   for (int i = 0; i < config.NumSamples; i++)
   {
       torch.Tensor single = generatedCpu[i];
       TileMap map = TileMapTensorConverter.FromOneHotTensor(single);
       maps.Add(map);
   }

TileMapTensorConverter.FromOneHotTensor produces a TileMap with the
correct Width, Height, and Tiles array, but DOES NOT set the
BiomeLabel field. C# default-initializes the public BiomeLabel field
to BiomeTypeEnum.Error (value 0, per standard-enum-zero-is-error).

Therefore every chunk in the returned list has BiomeLabel == Error
regardless of which biome was requested via config.BiomeLabel.

1.2 HOW THIS INTERACTED WITH THE BIOME-AWARE REPAIRS

The Iteration 7 BottomRowCompletion has the gate:

   if (chunk.BiomeLabel == BiomeTypeEnum.Treetop) return false;

The Iteration 7 CeilingCompletion has the gate:

   if (chunk.BiomeLabel != BiomeTypeEnum.Underground) return false;

Because the generated chunks always have BiomeLabel = Error:

   Error is not Treetop, so BottomRowCompletion ran on every chunk
   regardless of the requested biome. Treetop chunks got their
   bottom rows filled with Solid.

   Error is not Underground, so CeilingCompletion was a no-op on
   every chunk. Underground chunks never got a ceiling.

This explains exactly the visual symptoms reported: Treetop chunks
had continuous ground (BottomRowCompletion filled the gaps);
Underground chunks had no ceiling (CeilingCompletion never ran).

1.3 WHY THIS BUG WAS NOT CAUGHT BY THE 38 LOGIC TESTS

The Iteration 7 logic tests construct TileMap instances directly in
test code and EXPLICITLY set chunk.BiomeLabel = BiomeTypeEnum.Treetop
or chunk.BiomeLabel = BiomeTypeEnum.Underground before calling
RepairAll. Those tests exercise the biome-aware rules correctly
because the BiomeLabel is set in the test harness.

The defect lives in the MapGenerator code path that the logic tests
do not exercise. The integration test path - generate.exe running
TorchSharp inference, then calling FailureModeAnalyzer + repair - is
the only place the defect manifests, and there is no automated test
for that path because it requires GPU + libtorch + a checkpoint.

The Iteration 8 fix to MapGenerator is therefore code-level but
not currently covered by an automated test. Adding a generation-path
test would require either mocking the entire TorchSharp inference or
spinning up a fake EulerOdeSolverConfig path; both are out of scope
for the rascunho deadline.

1.4 THE FIX

In MapGenerator.Generate, after each TileMap is constructed from the
model output tensor, propagate the requested biome:

   TileMap map = TileMapTensorConverter.FromOneHotTensor(single);
   map.BiomeLabel = config.BiomeLabel;
   maps.Add(map);

One additional line of code. With this in place the Iteration 7
biome-aware repairs work as designed.

2.2 FIX 2: PIPE COUNT GUARANTEE

File modified: c2-pcg.flow-matching-eval/PipeSupportRepair.cs

The Iteration 7 PipeSupportRepair rejected any floating pipe whose
extension to ground would exceed config.MaxPipeRows = 6 rows. With
the model placing pipe tops at y = 2 to y = 4 most of the time and
the ground at y = 13 (after BottomRowCompletion), the typical pipe
column needs 10 to 12 rows, well above the cap. Result: almost
every pipe was REMOVED.

The fix gives MinCompletePerChunk priority over MaxPipeRows. When the
chunk has fewer than MinCompletePerChunk supported pipes, the next
floating pipe is extended regardless of resulting height. After the
minimum is satisfied, MaxPipeRows is enforced strictly so further
pipes do not pile up as multi-tile towers.

Trade-off: a typical chunk will now have exactly one tall pipe rather
than zero pipes. Visually a tall pipe is mildly unusual but it
matches some real SMB chunks (e.g. World 1-2 has a 7-tile pipe).

The override applies ONLY to pipes, not to bullet bills. Real SMB
Overworld levels frequently have chunks with no bullet bill cannons;
forcing at least one would over-populate the biome.

2.3 FIX 3: BULLET BILL LAUNCHER HORIZONTAL CLEARANCE

File created: c2-pcg.flow-matching-eval/BulletBillLauncherClearance.cs

Single-pass repair. For each BulletBillLauncher at (x, y), scans
cells (x - 3, y), (x - 2, y), (x - 1, y), (x + 1, y), (x + 2, y),
(x + 3, y). Solid and Breakable tiles in these cells are replaced
with Empty so the cannon has horizontal clearance to fire. Coin,
QuestionFull, Enemy, pipe parts, and other bullet bill parts in the
clearance zone are preserved (Coin/Question/Enemy are not
projectile obstructions; pipe and bullet bill parts belong to other
structures whose own validity passes handle conflicts).

The clearance applies only to the same row as the launcher because
in-game bullet bill trajectories are perfectly horizontal.

2.4 ORCHESTRATOR UPDATE

File modified: c2-pcg.flow-matching-eval/ChunkStructureRepair.cs

The pass list now contains 10 entries; BulletBillLauncherClearance
is inserted immediately after BulletBillSupportRepair so the
clearance only acts on launchers that survived support validation.

PART 5: LIMITATIONS
================================================================================

5.1 LAUNCHER CLEARANCE FIRING DIRECTION

In real SMB the bullet bill cannon fires only to the LEFT (the
direction Mario is moving away from). The current
BulletBillLauncherClearance clears BOTH sides because the canonical
SMB sprite is bidirectional in some sources and it is safer to clear
both sides than to leave a blocked side. A future refinement could
clear only the left if the rendered sprite supports a left-facing
direction-of-fire convention.

5.2 PIPE COUNT GUARANTEE WITHOUT EXISTENCE GUARANTEE

The MinCompletePerChunk override fires only when the model placed
at least one PipeTopLeft anywhere in the chunk. If the model produced
no pipe tiles at all, no pipe is added; the chunk has zero pipes.
This is fine for the thesis story because pipe density should
match the training distribution; we should not synthesize pipes
in chunks where the model decided they do not belong.

5.3 INTEGRATION TEST GAP

The biome propagation defect was not caught by the 38 Iteration 7
logic tests because they did not exercise the MapGenerator code
path. Adding integration tests requires GPU and trained checkpoint;
these are out of scope for the rascunho deadline but should be
added for the final submission to catch similar future defects.
